# Development secrets

Disposable PostgreSQL, RabbitMQ and simulator credentials are generated by
`pnpm dev:configure`. Existing values are retained so existing database volumes
continue to work. Every write replaces the env file atomically with mode `0600`;
symlink targets are rejected. Configuration changes do not rotate passwords
already stored inside PostgreSQL or RabbitMQ.

The development launcher reads the protected configuration and supplies secrets
only to the Compose process. Compose secrets with `environment` sources mount
credentials as files owned by the receiving runtime user, with mode `0400`.
Applications receive `NAME_FILE=/run/secrets/...` references. Container
configuration inspection therefore exposes file paths rather than credential
values. The host env file, launcher process and Docker daemon remain trusted.
Use a current Compose version supporting ownership and mode for environment
sources; this behaviour is exercised with the development stack. See
[Compose secret permissions](https://docs.docker.com/reference/compose-file/services/#secrets).

Each runtime supports either `NAME` or `NAME_FILE`, never both. Missing,
unreadable and empty files cause configuration failure without printing the
credential or path. One final newline is removed; other secret bytes are
preserved. File support stays in technical composition and adaptor code.

## Individual developer credentials

Credentials for a paid external provider are real secrets even when used for
development. Obtain a separate provider account or key per developer, with
provider-enforced scopes, revocation and spending controls where supported.
A non-production OpenBao agent or another approved credential manager can write
that key to a protected local file. The repository does not need access to a
production secret store and does not automatically contact paid providers.

For an optional integration, add its file reference to your local configuration,
for example `PROVIDER_KEY_FILE=/absolute/private/path/provider-key`. The launcher
requires an owner-only regular file; a relative path is resolved beside the env
file. It resolves the file in memory for Compose and retains only its path when
rewriting configuration. Configure the integration's Compose secret with
`environment: PROVIDER_KEY`, grant it only to the owning service and supply that
service with `PROVIDER_KEY_FILE=/run/secrets/provider_key`. For a service running
directly on the host, set `PROVIDER_KEY_FILE` to the protected file instead.

Do not paste the key into commands, commit it, print it in diagnostics or copy it
into the generated env file. Supplying a credential does not opt any normal test
into external calls: paid integration tests need an explicit separate invocation.
The current provider remains the local delivery simulator.

Secret files are read at application startup (and by applicable worker setup).
After replacing credentials, recreate the affected development containers so the
Compose secret and service connections use the new value. Live leased credential
renewal needs provider-specific connection replacement and is not implemented.
